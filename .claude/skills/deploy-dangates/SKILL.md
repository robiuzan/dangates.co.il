# Deploy

## The one thing to know

**Production is Cloudflare Pages via wrangler direct upload** — project `dangates`
(`dangates.pages.dev`), zone details in `docs/cloudflare-runbook.md`.

Pushing to `main` now publishes **nothing**. `.github/workflows/deploy.yml`, `public/CNAME` and
`public/.htaccess` were deleted 2026-09-06 with the `_redirects` cutover (commit `a0e0fe2`,
ADR 0004, backlog §12.4 / N5). Until then that workflow published a redirect-less copy of the site
to GitHub Pages on every push — a real deployment nobody saw, because the domain no longer resolved
there. `edge.mjs` → `deadHostArtifacts 0` holds the line; wrangler direct upload is the only path to
production.

Verified 2026-08-16 from live headers (`Server: cloudflare`, `cf-cache-status: DYNAMIC`, no
GitHub/Fastly edge headers) and re-verified 2026-08-23 in the runbook. The roster's
`hosting.target: cloudflare-pages` / `pagesProject: dangates` is right; its `toolkit.notes` "LIVE on
GitHub Pages" is stale — fix the note, don't follow it.

## The command — and the exact form the guard hook accepts

Deploying is a **production mutation**. It runs dry first, and the user says go, every time.
`.claude/hooks/guard-destructive-ops.ps1` blocks any Bash/PowerShell call whose text matches
`deploy-site.ps1` or `wrangler pages deploy` unless the command carries `-DryRun`, **or** carries
`-Confirm` **and** a `# APPROVED: <reason>` marker in the same command:

```powershell
# 1. preview — safe, changes nothing, always first
powershell -File "c:/Users/robiu/antigravity/Projects/Israeli services sites/ops/deploy-site.ps1" -Domain dangates.co.il -DryRun

# 2. execute — only after the user's explicit go-ahead in this conversation
powershell -File "c:/Users/robiu/antigravity/Projects/Israeli services sites/ops/deploy-site.ps1" -Domain dangates.co.il -Confirm   # APPROVED: <what the user approved, in their words>
```

The marker is a trailing shell comment on the **same** command line; the hook regex is
`-Confirm` + `#\s*APPROVED:` anywhere in the text. Never fake the marker — it records that a human
approved this deploy in this session. Other flags: `-BuildOnly` (build + output gate, no upload),
`-DeployOnly` (ship the existing `out/` as-is), `-SkipDriftCheck` (only when the roster is knowingly
ahead of DNS), `-All` (every roster site — never for a dangates task).

> The hook matches the command **text**, so even a `grep` or `sed` whose argument names the script is
> blocked. Inspect `deploy-site.ps1` with the Read tool, not with a shell one-liner.

## What the script does, and why each step exists

1. Resolves the Pages project from the roster (`dangates`).
2. **Drift check** — asks the Cloudflare API whether that project actually serves this domain. This
   is the guard against a wrangler push into a project nothing resolves to, which reports success
   while changing nothing public.
3. Reinstalls the vendored kit by path and clears `.next/` when the kit changed (the two traps below).
4. `npm run build`.
5. **Output gate** on `out/` — refuses a broken or stale export (including a manifest `images.hero`
   with no `/cdn-cgi/image/` URL in the HTML, the classic stale-cache signature).
6. Preserves the previous `out/` as `out.prev/` so a rollback is one command.
7. `npx wrangler pages deploy .\out --project-name dangates --branch main`.
8. Appends the result to the hub's `logs/deploys.csv`.

## The two staleness traps

Both produce a **successful build of the wrong code** with no error anywhere:

- **npm caches `file:` tarballs.** `@ishub/site-kit` is `vendor/ishub-site-kit-0.0.0.tgz`. A fresh
  tarball plus a plain `npm install` keeps serving the **old** kit from cache.
- **Next caches compiled modules under `.next/`.** Even with correct `node_modules`, a rebuild can
  emit the previous kit's markup — observed on this fleet.

If you build manually before deploying, clear the cache first (`rm -rf` is hook-blocked; `out/` is
regenerated by the build and is a protected path):

```bash
node -e "require('fs').rmSync('.next',{recursive:true,force:true})" && npm run build
```

## Before you deploy

1. **`npm run audit:env`** — 0 failures (dead citations, frontmatter, hooks, deny set).
2. **`/qa-build-gate` end to end** — clean rebuild, `npm run gate`, the auditor sweep. The gate is
   judged on **regressions** against the known-baseline table in that skill, not on a zero exit code;
   a failure absent from the latest `docs/audits/` report does not ship.
3. **Roster check** — `powershell -File "c:/Users/robiu/antigravity/Projects/Israeli services sites/ops/validate-manifests.ps1"`.
   Read-only; exit code = ERROR count. It enforces the single-source-of-truth contract, including
   the `phoneOverride` rule — dangates is the one site legitimately off the shared lead number.
4. **Redirect map touched?** `npm run redirects` regenerates `public/_redirects` from `REDIRECTS.md`
   and `prebuild` runs it anyway, but commit the regenerated file — `git status --porcelain public/`
   must be clean before you build, or the map and the shipped rules have drifted (§1.6). `public/`
   reaches `out/` only through a build.
5. **Did visible copy change? Bump its `updated` date — no script catches this.** `<lastmod>` comes
   from `services[].updated`, `locationsUpdated`, `staticPages[].updated` and a post's `updated`.
   `links.mjs` asserts each is a real, non-future date, **not that it is current**, so a stale date
   survives a green gate and understates a real change on exactly the pages you want recrawled.
   Judge it per page type: rendered copy changed → bump; metadata, analytics, styling or a verbatim
   refactor → leave it. Client-only UI that is absent from the crawled bytes (the lead form's error
   block) is not a copy change — check the built HTML rather than the component. Precedent:
   2026-09-06 bumped the seven services for the per-service trigger lists and nothing else.
6. **Stop-ship, all script-proven:** a doubled `<title>` or missing canonical (`titles.mjs`); a live
   🔶/⛔ claim (`claims-grep.mjs`); `Review`/`AggregateRating` or an `author` key reappearing
   (`schema.mjs` fails — the review block is gated in code, golden rule 1); a container id change
   without the `gtm.js` 200-check (golden rule 8).

### The legacy-URL 301 probe — run it on every deploy

Since ADR 0004 landed in the repo (2026-09-06, commit `a0e0fe2`) the legacy URLs are **real 301s**
from `public/_redirects`, not meta-refresh stubs. Probe one legacy URL from each section of
`REDIRECTS.md` and expect `301` + `Location` with the query string preserved:

```bash
for p in "/%D7%AA%D7%9C-%D7%90%D7%91%D7%99%D7%91/?utm_source=test" \
         "/%D7%A9%D7%A2%D7%A8%D7%99%D7%9D-%D7%97%D7%A9%D7%9E%D7%9C%D7%99%D7%99%D7%9D-%D7%94%D7%A9%D7%A7%D7%A2%D7%94-%D7%A9%D7%9E%D7%97%D7%96%D7%99%D7%A8%D7%94-%D7%90%D7%AA-%D7%A2%D7%A6%D7%9E%D7%94-%D7%95%D7%9E%D7%94-%D7%9B%D7%93%D7%90%D7%99-%D7%9C%D7%93%D7%A2%D7%AA/" \
         "/contact/"; do
  curl -sSI "https://dangates.co.il$p" | grep -iE '^HTTP|^location'
done
# expect: 301 → /locations/תל-אביב/ (query kept) · 301 → /blog/שערים-חשמליים-השקעה/ · 301 → /צור-קשר/
```

A `200` on any of the three means either `_redirects` did not ship or a static asset is shadowing
its own rule — `find public -name index.html` must be 0, and a stub returning would be exactly that
failure. Purge the Cloudflare cache and re-probe before concluding anything. `?utm_source=test`
surviving into `Location` is the §13.3 acceptance test: a 301 preserves the query string where the
old `location.replace()` stub destroyed it, so paid and campaign attribution on legacy links is only
actually fixed once this probe passes live.

**The first deploy after Sprint 1 is the one that makes this real.** As of 2026-09-06 the 72 rules
and `public/_headers` exist only in the repo — `edge.mjs` measures files, not responses.

**AI-crawler state and `robots.txt`:** do not restate it here — it moved on 2026-08-23 (managed
`robots.txt` off, edge 403) and again by 2026-09-06 (every AI crawler 200 — backlog §6.1 ✅).
`docs/cloudflare-runbook.md` step 1 carries the current state, the decision table and the full-UA
probe loop; reading `robots.txt` alone proves nothing. The per-bot list in `app/robots.ts` (commit `6f4a1a8`) has been live since the Sprint 0 deploy on 2026-09-06 — the post-deploy verification checks it stays.

## Response headers — this repo owns them since 2026-09-06

`public/_headers` (commit `a0e0fe2`, ADR 0004, backlog §12.1) declares HSTS, `X-Frame-Options`,
`X-Content-Type-Options`, `Referrer-Policy`, `Permissions-Policy`, `/_next/static/*` immutable
caching and a **report-only** CSP. Before that the live headers came from Cloudflare zone rules and
Pages defaults, and a deploy neither set nor preserved them.

Cloudflare Pages **merges** `_headers` with the zone rule rather than replacing it, so a header can
be emitted twice until the owner deletes the rule (`docs/owner-actions.md` §1.3, runbook step 4).
Verify against the live response after the deploy, never against the file —
and check `dangates.pages.dev` too, because it has no zone rules in front of it, so a header showing
there proves the repo is the source:

```bash
curl -sSI https://dangates.co.il/     | grep -iE 'strict-transport|content-security|x-frame|permissions|referrer|content-type-options'
curl -sSI https://dangates.pages.dev/ | grep -iE 'strict-transport|x-frame|permissions'
```

The CSP is report-only on purpose: a static export cannot mint a per-request nonce for the inline
GTM snippet, and an enforcing `script-src` that gets it wrong kills every conversion signal while the
pages still look fine. Watch the browser console over a week of real traffic — including one real
form submission, one tracked call click and one legacy-URL hit — before switching it to enforcing
(§12.2 stays PARTIAL until then). `edge.mjs` measures the file; only the two curls measure reality.

## Rollback

`out.prev/` holds the previous export (a protected path — read it, never edit it). Two ways back:

- `npx wrangler pages deploy .\out.prev --project-name dangates --branch main` — the line the script
  prints; it is hook-gated exactly like a deploy (`-Confirm` + `# APPROVED:`), because it is one.
- The Cloudflare Pages dashboard keeps prior deployments and can roll back in one click — usually
  faster. Offer both; the user chooses.

## Rules

- **Never deploy without being asked.** Not as the last step of a task, not "while I'm here". Dry run
  first, every time; the `# APPROVED:` marker only after the user's go-ahead in this conversation.
- Never use `-SkipDriftCheck` to make a failing deploy pass — a drift failure means the deploy would
  have gone somewhere nobody can see.
- Never edit `site.config.json` as part of a deploy — it syncs from the roster (hook-blocked anyway).
- Never deploy with `/qa-build-gate` stop-ship items outstanding or a gate regression.
- Zone settings (AI-crawler policy, cache rules, security headers, Scrape Shield, DNS) are the
  owner's — `docs/owner-actions.md` §1 and the runbook document the toggle; a deploy never touches
  them, and the hook blocks Cloudflare API calls.
